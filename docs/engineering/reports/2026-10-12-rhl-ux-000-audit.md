## Executive summary

The React client already uses the intended v0.1 topology: one local Node Runtime, Pi SDK sessions, HTTP JSON commands, a normalized SSE stream for conversation events, and HTTP polling for WorkflowRun state. Pi conversation sessions are persistent in the production Runtime and can be listed, switched, and restored. WorkflowRun objects are a separate in-memory Application service; reports and ResearchBundles have their own persistence paths.

The reported UX gaps have distinct causes and boundaries:

1. A submitted prompt is not rendered optimistically. In the current path the client first waits for `/api/research/dispatch`, then may submit a Pi prompt, and only reloads persisted messages after Agent completion/error. This permits a long blank interval. An explicitly selected Workflow follows the dispatch path and does not submit the text to Pi at all, so the text is not stored as a conversation message.
2. The conversation list is persisted Pi session metadata, not a list of WorkflowRuns. Chat-dispatched runs have no `conversationId` field or session metadata link. The exact reported Company Research run was not repeated with authenticated live inputs; this structural omission is visible in the real source path and must be addressed in UX-001 before a client-only history patch.
3. SSE has useful safe Agent/message/tool events and native EventSource reconnect, but no event replay buffer, durable event log, message/operation correlation, or Workflow events. Reconnection triggers a conversation snapshot read; it cannot replay missed deltas.
4. Workflow status is currently in memory. The UI can poll a known run ID, cancel it, and open verified output artifacts. `currentStage` is optional but the current WorkflowService does not set it. Chat dispatch does not persist its run ID for refresh recovery. Runtime restart loses status, while separately persisted reports/bundles may remain.

The audit did not find `company_deep_research` in the checked source/test trees. The current ResearchDispatch registry ID is `company_research` with the English label “Company Research”; use this registry ID internally and keep any localized display name separate.

## C. Session lifecycle findings

### Creation, persistence, messages and list

- Production Application Runtime injects `SessionManager.create(cwd, sessionDir)` into `ResearchHubSessionRuntime`; normal app use is persistent. The in-memory default in `app/pi/session.ts` is a test/fallback path, not the production configuration.
- `POST /api/conversations/new` creates a Pi session; `POST /api/conversations/switch` locates its path through `SessionManager.list` and switches. `GET /api/conversations`, `/current`, and `/messages` query Pi session metadata/messages.
- Pi owns persisted transcript. `toSafeConversationMessage` permits user/assistant text and fixed product-tool summaries; non-product tool payloads are omitted. Messages are returned from `currentSession.messages`.
- The list is sorted by Pi session modification time, descending, then ID. It contains `conversationId`, optional name, `updatedAt`, message count, and active flag. It is not joined to WorkflowRun data.
- Existing focused Runtime test `Slice A uses persistent Pi sessions and restores a prior conversation` passes. Therefore the general Pi persistence/switch path exists; it does not cover the dispatched Workflow association gap.

### Titles, rename and archive

Pi `sessionName` and `SessionManager.list().name` are the only title sources observed. Create accepts an optional name and appends session info; UI creates with no name. There is no rename/archive/restore endpoint, archived flag, title source, version, or concurrency guard in the ResearchHub adapter. No automatic title update exists.

Recommended storage: prefer the existing Pi session metadata path and serialize updates through the single Runtime adapter. Avoid a parallel transcript store. Confirm the installed Pi SDK's supported session-info update semantics when choosing the concrete representation; candidate fields from the taskbook remain design candidates, not schema commitments. Use a monotonic metadata revision (or an equivalent Runtime compare-and-set) so a late Workflow event cannot override a USER title, including when the user chooses “新对话”.

### Workflow/session association and historical case

Direct dispatch carries query/mode/policy, creates a `runId`, and invokes a registered Workflow. The HTTP payload has no conversation identity; run contracts have no `conversationId`; no update is made to Pi session metadata. The conversation list queries Pi only. The actual Company Research report from the taskbook was not rerun with live sources or a real user Knowledge Base and remains `NOT_REPRODUCED`. The deterministic source path explains a reliable way the symptom can occur, but does not identify any other historical or environment-specific failure.

### Connection and duplicate behavior

`RuntimeClient.openEvents` uses native `EventSource`; EventSource retries by default. On `open`, the client calls `syncCurrent`, which fetches current state/messages/list. The server has a 15-second heartbeat and bounded subscriber/backpressure queues, but no frame history or Last-Event-ID replay. The adapter event ID is composed from conversation ID and a process-local incrementing sequence for that adapter; a new connection/adapter is not a persistent sequence. UI transcript keys use timestamp plus array index. There is no explicit deduplication/reconciliation by message or operation ID. The focused event tests confirm safe projection, cleanup and backpressure, not replay.

## H. CTO decisions and remaining risks

The CTO conditionally approved the audit and closed the five architecture decisions below for the UX-001–004 plan:

1. **Workflow/session ownership:** every accepted Workflow request must be associated with a recoverable Pi session. UX-001 owns the server-side session identity, request record, and Workflow-run link; the client must not synthesize history state.
2. **Workflow identity and display:** use the real ID from the current registry (`company_research`) as the internal identity. Keep localized display names separate from registry IDs; do not revive `company_deep_research` as an assumed current ID.
3. **Session metadata:** prefer existing Pi Session metadata for title, title provenance, and archive state. Keep metadata updates server-owned and concurrency-safe; do not add a separate transcript store or Knowledge Schema fields.
4. **Workflow recovery boundary:** UX-003 must restore an in-memory run after a page refresh while the same Runtime process remains alive. Recovery across Runtime restart is a separate, stronger persistence scope and is not promised by this plan.
5. **Progress/data contract:** expose only stages, timing, tool/data availability, and outcomes emitted by the owning Workflow/provider. Stage lists are producer-defined; do not infer stage counts, progress percentages, or unavailable data.

The existing Vite bundle-size warning is unrelated to this audit. No performance optimization was attempted. No unresolved architecture decision blocks the next separately authorized implementation task; CTO final acceptance remains pending.
