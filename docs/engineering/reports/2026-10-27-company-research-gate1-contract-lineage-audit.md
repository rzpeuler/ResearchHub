# Company Research Gate 1 — Skill contracts and canonical field lineage

Date: 2026-10-27. Scope: read-only comparison of the ten current Company Research atomic methods and the four existing Company data requirements, plus the cross-Workflow valuation/estimate routes relevant to P0-19. This records implementation evidence and gaps; it is not a Gate 1 acceptance or a claim that the new Valuation, Bull/Base/Bear, or Variant Perception input contracts are sufficient.

## Evidence and interpretation

The task brief requires exact source, period, unit, evidence, numerical, PIT, missing-data, retry, and model boundaries. Current code is authoritative for executable behavior; each Skill document is methodology guidance. A declared requirement/source policy proves configuration only. It does not prove a provider returned usable, PIT-eligible values for BYD or Dongshan. This report began as a code-only desk audit; measured Runtime/API coverage is added in section 4.

The raw-key alias, normalized-field, metadata-inference, consumer, and conflict-policy detail for all four requirements is in [the field-level lineage appendix](2026-10-27-company-research-gate1-field-lineage-detail.md). Estimate point-version and EPS-definition contract design is in [the P0-19 input contract proposal](../specs/2026-10-27-company-research-p0-19-input-contract-proposal.md); that proposal is not an implementation or approval of a runtime schema change.

Common executable method contract: `skills/company-research/methods.ts:353-400,1393-1412,1908-1993`. The Workflow assigns stable section ownership (`:355-358`), injects a selected packet of citation-eligible excerpts and optional `preparedAnalysis` (`:1355-1412`), then invokes the configured `ReasoningExecutor`; the Skill itself has no provider I/O, KB writes, or sibling-Skill calls. The model returns exactly seven top-level fields (`status`, `answer`, `markdown`, `sections`, `findings`, `limitations`, `risks`), with exact owned section IDs. Status is `complete` or `insufficient_evidence`; citations must resolve to the exact supplied source ID and paragraph, every complete section and complete summary needs located citations, findings need evidence, and insufficient evidence needs limitations. Numeric grounding, table/source-row binding, and deterministic prepared results are checked after parsing. Calls are bounded by `maxAttempts` 1–2 (default 2), with Workflow controlling retries. That `complete` is method-wide is a known limitation: the schema does not encode per-section completeness or a validated minimum substantive-depth measure.

The shared executor contract requires source dates and exact locators; a complete method must cite each owned section. Inference/assumption labels are allowed but do not make an unsupported numeric input true. Model-generated output is semantic explanation only; arithmetic, source identity, schema bounds, and numeric grounding remain code-owned. Neither method status nor citation count alone proves semantic adequacy.

### Cross-Skill status and boundary gaps

- The current registry is ten methods and exact owners above; the 19-section report contract is separate from these method contracts. `management-capital-allocation` is shared with no subowner declaration/merge behavior in the map.
- `status` applies to the entire method result, not each owned section. It is possible for a supported sibling section to be represented under an overall insufficient/failed method; report aggregation semantics require separate review.
- Executable schema checks shape, ownership, citation resolvability and bounded fields, but not a general minimum substantive analysis rubric. Independent report review is another Workflow gate and must not be inferred from a method's `complete` status.
- Methods do not own acquisition or provider retries. The shared default is at most two semantic calls; acquisition retry and review budgets are separately Workflow-owned. Per-skill actual invocation counts require a run artifact.
- The model provider/model identity is selected in Runtime composition and recorded in run context; Skill contract itself is model-agnostic. This audit did not inspect an acceptance run's actual model invocation.
